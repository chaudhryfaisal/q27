# Performance experiments after the sampler: September 10–12, 2026

The next inexpensive code improvement is a bounded BPE-result cache. A local
prototype preserves token IDs and replay outputs and saves about 20 ms of warm
request TTFT. Raising the prefix-cache entry limit to 128K protects long,
interleaved conversations from multi-second re-prefills, at a substantial host
memory cost. Neither result accounts for the remaining agent trajectory gap.
Keep seven DFlash2 draft tokens: the depth sweep did not find a dependable win.

These are local experiments, not deployed changes. The prototype, scripts,
logs, and profiles are in `build/perf-next-20260910/` in the q27-master worktree.
The working-tree change is this report; prototypes stay under `build/`.
Production uses its original binary and configuration after each experiment batch.

## Measurement setup

- 32 completed server trials, 414 requests, plus the CPU corpus and Unicode
  parity runs. The failed initial NInfer attempt is excluded from these totals.
- RTX 5090, UUID `GPU-e592b842-7233-7971-56b7-a14bd38a58e6`; the RTX 3090
  transcription services were left running and untouched.
- q27 target weights `qwen38-27b-mtp.q27`, FP8 KV, DFlash2 Q8 drafter, full
  proposal head, temperature 1, top-p .95, top-k 20, min-p .05, unlimited
  thinking, one serving slot. Device weight checksum `b743d26b1f0562a9`
  passed at every q27 boot.
- Every trial starts a fresh server and private tmpfs prefix cache. The main
  replay has eight synthetic requests capped at 400 output tokens, followed by
  twelve recorded Claude Code requests. Repeated arms use the same ordering.
  Input recordings are `build/reqlog-{gate,echo}.jsonl` in the original worktree.
- Longer-context tests use four recorded q27tokb states, in recording order
  87, 203, 214, 219: **36,962 / 51,694 / 69,127 / 28,701 prompt tokens**.
  Each request is capped at 1,024 output tokens unless stated otherwise.
- TTFT starts **before the HTTP POST** and ends at the first content delta or
  tool block. SSE parsing uses one-byte chunks. The older replay utility's
  timer started after response headers and was unsuitable for this measurement.
- Reported throughput is total generated tokens divided by total decode time.
  Changing draft depth changes the random stream and output lengths, so a
  faster blended throughput or shorter request is not automatically a win.
- Controls bracket candidates where noted. GPU temperatures reached 88°C and
  clocks varied; approximately 1–3% GPU differences need caution. No clock,
  fan, production configuration, or service-file changes were made.

Production was v0.11.4; the first release/depth/cache trials were v0.11.5 at
`08382b6`. Master acquired wait diagnostics at `8cd7083` between batches.
The final tokenizer A/B rebuilt the candidate against `8cd7083` and verified
the baseline binary hash before and after each trial. The earlier mixed-commit
`host-*` trials are not used for the final wall comparison.

## BPE cache: reliable CPU and TTFT savings, small total wall effect

The isolated `tokenizer_cached.cpp` prototype memoizes the exact pretokenized
word's BPE IDs per Tokenizer instance. It uses a mutex and a 16,384-entry map,
cleared when full. The existing 1,024-byte word bound remains in force. It
does not cache rendered prompts or change normalization, token matching,
sampling, or GPU kernels. This is a bounded prototype, not a tuned eviction
policy; concurrent scaling and adversarial cache churn were not benchmarked.

The CPU corpus is all 280 recorded q27tokb requests: 40,329,220 rendered bytes
and 10,346,011 token IDs per pass, three passes each.

| CPU work per request | Baseline | BPE cache prototype |
|---|---:|---:|
| Render + encode + current duplicate system encoding | 38.24–39.26 ms | 11.80–11.87 ms |
| Render + encode, excluding duplicate system encoding | 24.97–25.50 ms | 8.85–8.95 ms |

The second row is an accounting estimate of eliminating redundant work, not
a server implementation of that change. The microbenchmark also checks a
system/history split and can prime cached words during a pass; use the server
comparison below for actual serving impact.

All six full-corpus token hashes equal `3784602603087288111`. The candidate
also passed HF token-ID parity on **200,000 mixed-Unicode** and **99,699 NFD**
cases using `tools/tok_parity.py --sets mix,nfd`.

Fresh-server A/B/B/A on the same `8cd7083` source:

| Measurement, 20-request replay | Baseline A / B | Cached A / B |
|---|---:|---:|
| Front-end `tok_ms`, total | 358 / 363 ms | 106 / 103 ms |
| Decode time, total | 25.114 / 25.373 s | 25.448 / 25.449 s |
| Prefill time, total | 18.848 / 19.152 s | 19.071 / 19.097 s |
| HTTP wall, total | 44.383 / 44.951 s | 44.686 / 44.711 s |
| Warm CC TTFT, mean per arm | 303.70 / 306.33 ms | 285.85 / 284.92 ms |

Warm here means the eleven CC requests requiring fewer than 2,048 prefill
tokens. Mean TTFT falls **19.63 ms (6.4%)**. Front-end time falls **71.0%**.
All four runs produce the same 20 output hashes, 6,042 tokens, and 1,438
speculative rounds. Overall HTTP wall is **0.07% higher** for the prototype,
well within GPU drift; this run does not establish a total wall-time win.
The CPU improvement is real, but it cannot explain a multi-fold agent gap.

## Prefix-cache entry cap: a large long-session tail win

Controlled A/B/B/A: serve state 214 at 69,127 tokens with max_tokens=512,
serve an unrelated tiny conversation, then return to exactly the same state.
Both arms receive a **16 GB cache budget**, with only the per-entry token cap
changed from 65,536 to 131,072.

| Returning to the evicted conversation | 65,536 cap, A / B | 131,072 cap, A / B |
|---|---:|---:|
| Prefix hit | 23,552 tokens | 69,122 tokens |
| Tokens requiring prefill | 45,575 | 5 |
| Prefill phase | 16.316 / 16.372 s | .410 / .403 s |
| HTTP TTFT | 16.413 / 16.466 s | .505 / .498 s |

The larger cap saves **15.94 seconds to first token, about 97%**, in this
case. The 65K arm can save only the shared system prefix. The 128K arm saves
the stable 69,122-token conversation prefix, about 2.56 GB. Saving costs
about 106–107 ms; restoring reads it in 226–234 ms and imports it in 125 ms.

Pinned staging grows from **2 × 2.44 GB to 2 × 4.72 GB**, approximately
**4.56 GB more pinned host memory**. More large entries also consume cache
capacity sooner. All cold-state outputs match. Returning through different
checkpoint/drafter history produces 360 versus 247 output tokens, so the
claim is about prefix reuse and TTFT, not equivalent task-completion wall or
quality. Each configuration repeats its own output deterministically.

This tail was rare in the recent campaigns. Counting requests above 65,536
prompt tokens that recomputed more than 8,192 tokens:

| Existing campaign | All requests | Above 65K | Above 65K with >8K recomputed |
|---|---:|---:|---:|
| q27tok | 283 | 6 | 0 |
| q27tokb | 280 | 10 | 0 |
| q27toklow | 291 | 39 | 1, 4.6 s prefill |
| q27v0113c | 277 | 35 | 3, 18.9 s prefill |

These are incidence counts, not proof that every counted miss would be cured
by the larger cap. The result favors 128K entries for long/interleaved use
when the host-memory budget permits, but the latest two campaigns provide
no evidence that this cap caused their average wall gap.

## Draft-depth sweep: retain K=7

| Draft tokens | Full replay decode tok/s | Fixed 400-token subset tok/s |
|---|---:|---:|
| 5 | 222.8 | 214.7 |
| 7, control A | 237.6 | 231.9 |
| 8 | 232.3 | 214.0 |
| 9 | 251.9 | 228.8 |
| 11 | 228.8 | 207.5 |
| 7, control B | 238.3 | 232.5 |

K=9's apparent aggregate improvement comes with a different work mix: 5,189
versus 6,042 output tokens. It loses on the fixed-length subset. A separate
K7/K9/K9/K7 test on the four longer states gives pooled **212.8 tok/s at K7
versus 211.6 at K9**. The longer K8 test gives 204.1 tok/s. Neither justifies
a new global depth default. A future adaptive policy would need held-out
contexts and quality checks; this sweep has not validated one.

Production v0.11.4 and release v0.11.5 K7 generated identical output hashes
and round counts on all 20 requests. Decode throughput was 238.4 versus
237.6–238.3 tok/s. The shipped Unicode/tokenizer followups did not introduce
a measurable regression on this replay.

## Decode profile: verification dominates; sampler work is mostly exhausted

Nsight node-level CUDA graph traces cover one 28,701-token state (176 rounds)
and one 69,127-token state (81 rounds). The filenames `profile-30k` and
`profile-80k` are approximate labels; the second actual prompt is 69K.
Tracing roughly doubles decode wall time, so these traces locate GPU work;
they are not end-to-end speed measurements.

| GPU kernel time per speculative round | 28.7K context | 69.1K context |
|---|---:|---:|
| Target verify graph, all kernels | 14.711 ms | 15.714 ms |
| Main Q4 target projections, within verify | 9.086 ms | 9.079 ms |
| Target attention, within verify | 1.128 ms | 2.156 ms |
| Target RMSNorm/quantize, within verify | .828 ms | .827 ms |
| GDN recurrence, within verify | .781 ms | .779 ms |
| Multi-lane nucleus sampler, within verify | .244 ms | .241 ms |
| Drafter graph, all kernels | 2.412 ms | 2.419 ms |

Rows within verify overlap its total and must not be added to it. Other
graphs and streams also overlap. Verify has 1,643 kernel nodes per round;
the drafter has 159. Drafter Q8 GEMVs account for about 1.37 ms and its full
proposal head about .48 ms. Unprofiled D2 timing is consistent with roughly
2.44 ms draft, 14.6–15.8 ms verify, and .22 ms host work.

The sampler is now only about **1.3% of summed GPU kernel duration**.
Even eliminating it cannot deliver a large engine win. The remaining decode
targets are verification weight traffic/projections, attention at longer
contexts, and norm/quantize/reduction fusion. A 10% projection improvement
would save about .9 ms of measured kernel work; that is a budget estimate,
not a demonstrated speedup. Prior CTA-count and proposal-head sweeps already
failed to provide a general win; repeat them only with a new mechanism.
Large kernel share does not establish spare headroom: the earlier
[GEMV investigation](perf-attribution-decode-2026-09-07.md) found memory and
register limits on the dominant projections.

## Fresh NInfer comparison: cold prefill is still the clear engine gap

The installed NInfer build is commit `487f897`, dated September 6, with the
NVFP4 release artifact, INT8 KV, 131,072-token capacity/context, DFlash2,
seven drafts, full proposal head, and its default device/host context cache.
This is a comparison against the installed competitor, not a claim about
NInfer's latest upstream version. Sampling is explicitly matched at T=1,
top-p=.95, top-k=20, min-p=.05, presence/frequency penalty zero, seed zero
unless a recorded request supplies a seed. q27 uses its production defaults
and 65K-entry/4 GB private tmpfs cache for these trials.

The common replay excludes `gate-8` and `echo-0`, two small title requests
with `output_config.format` that this NInfer build rejects. Its OpenAI model
ID is set to `qwen38` to accept the existing request. The first failed attempt
used a different public model ID and returned 404 before generation; it
contributes no timing results. Both engines receive the remaining eighteen
request bodies in the same order, without content or sampling changes.

| Full 18-request replay | q27 A / B | NInfer A / B |
|---|---:|---:|
| Output tokens | 5,593 / 5,593 | 5,251 / 5,251 |
| Speculative rounds | 1,336 / 1,336 | 1,297 / 1,297 |
| Decode tok/s | 237.4 / 236.8 | 222.4 / 221.7 |
| Decode wall | 23.556 / 23.615 s | 23.607 / 23.689 s |
| Prefill wall | 19.277 / 19.537 s | 15.108 / 15.273 s |
| HTTP wall | 43.245 / 43.566 s | 39.281 / 39.529 s |
| Computed prefill tokens | 69,244 | 98,121 |

Each engine repeats its own output hashes exactly. The engines produce
different outputs and use different continuation-cache policies. In particular,
NInfer keeps returning to the same earlier turn-closure prefix on several
recorded q27 histories, while q27 advances its saved pre-decode prefix.
This is an off-policy replay, not a live conversation driven by each engine's
own outputs, so do not extrapolate this cache disadvantage to NInfer's real
agent workloads. The four longer states show the same limitation: q27
prefills 93,835 tokens in 30.505 s, NInfer 139,287 in 32.140 s; aggregate
wall there is not a comparison of equal prefill work.

The cleanest comparison is **cold prefill**, where both have zero prefix hits:

| Cold prompt size, q27 / NInfer | q27 prefill | NInfer prefill | q27/NInfer time |
|---|---:|---:|---:|
| 2,259 / 2,252 tokens, eight observations per engine | .621 s | .297 s | 2.09× |
| 6,588 / 6,581 tokens, eight observations per engine | 1.698 s | .787 s | 2.16× |
| 25,279 / 25,398 tokens, two observations per engine | 6.894 s | 3.610 s | 1.91× |
| 36,962 / 37,091 tokens, one observation per engine | 10.631 s | 6.427 s | 1.65× |

Means are used above. Prompt rendering is not token-identical across engines:
NInfer has seven fewer tokens on the synthetic prompts and 119–134 more on
the CC states. These small length differences do not explain the cold-prefill
gap, but this is not a numerical-equivalence or output-quality test.

The eight fixed-output requests generate 3,200 tokens on both engines.
q27 decodes them at **233.7 / 232.8 tok/s**, NInfer at **206.0 / 205.3 tok/s**.
Even there NInfer has lower total request wall because prefill more than
offsets q27's decode advantage. Different tokens and acceptance rates remain
a limit on interpreting decode ratios as pure kernel performance.

## What to do next

| Priority | Work | Evidence and next acceptance check |
|---|---|---|
| Small code improvement | Bounded BPE cache, then avoid encoding the system block twice | About 20 ms less warm TTFT; identical token IDs and server outputs. Integrate a bounded policy, verify concurrency/cache churn, and retain full Unicode parity. |
| Long-session protection | Consider 128K prefix-cache entries where host memory permits | The eviction test saves 15.94 s TTFT; budget about 4.56 GB more pinned staging plus larger cache blobs. Measure incidence and memory pressure on the intended workload. |
| Larger GPU project | Cold-prefill W4A8 GEMM and attention | Fresh NInfer measurements retain a substantial cold-prefill advantage. Benchmark complete prefill including quantization, scale folding, and tail work before claiming a gain. |
| Agent wall-time investigation | Explain the first trajectory divergence on paired tasks | The earlier campaign still has roughly twice as many q27 turns. Pair rendered inputs/token IDs and first differing decisions, then measure successful task wall with actual tests. These replays do not establish a quality-preserving way to shorten trajectories. |
| Lower priority | More sampler work or a global draft-depth change | Sampler is .24 ms; K5/8/9/11 did not establish a dependable improvement over K7. |

The previous [prefill attack](plans/2026-09-08-prefill-attack.md) already tried
a TMA W/X-only kernel: 1.33–1.39× on two projection shapes, below its 1.6×
adoption threshold. The fresh gap is a reason to pursue a different mechanism,
not evidence that rerunning that same spike will close it. A native FP4
weight tier would also change numerics and needs a separate quality decision.
