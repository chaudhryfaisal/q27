# 5-bit K / 3-bit V KV cache (turbo5k) -- implementation plan

**Status:** filed, not started. Written 2026-08-01 to survive a context clear.
**Motivating measurement:** BUILDLOG 2026-08-01 (KV tail study), commit `bbec4a2`.

## Why

The 08-01 tail study measured every KV format against an **fp16 reference** on a
64K slice of the 154K agentic corpus (`scratchpad/t3_quality/corpus/agentic_req0031.i32`):

    format    KB/tok    dPPL     mean|d|   p99.9   |d|>1   catastrophic
    fp16        68.0    ref        --       --      --        --
    fp8         34.0   +0.458%   0.14612  5.4287   2718        19
    turbo3v     41.0   +0.510%   0.20971  7.0938   4321        52
    turbo3      14.1   +0.804%   0.27673  8.7321   5816       114

("catastrophic" = fp16 NLL < 0.1 and the format's NLL > 1.0, i.e. the reference
is confident and the format is badly wrong. It is a threshold on teacher-forced
NLL, so it bounds where damage COULD occur -- it does not demonstrate a broken
JSON key downstream.)

Three facts drive this plan:

1. **turbo3 carries 6.0x fp8's catastrophic-position count at a dPPL of
   +0.804%.** PPL cannot see this. Any tier decision made on PPL alone on the
   KV axis is uninformed.
2. **Spending bits on K is the right direction.** turbo3v (fp16 K + turbo3 V)
   cuts catastrophic 114 -> 52 and mean |d| by 24%.
3. **But fp16 K is a sledgehammer.** K is half the cache, so turbo3v lands at
   41.0 KB/tok -- BIGGER than fp8's 34.0 and worse on every metric. It is
   Pareto-dominated and stays diagnostic.

q27 currently jumps 3-bit -> fp8/fp16 with nothing between. Every best-value
config in anbeeld's KV benchmarks (q5_0/q4_1, q6_0/q5_0) lives in the 5-6 bit
band we skip. **A 5-bit K paired with the existing 3-bit V is the missing rung.**

## Target

    turbo5k = 5-bit K + turbo3 V     projected ~24 KB/tok

Sizing: turbo3 is 14.1 KB/tok symmetric, so K and V are ~7.05 each. A 5-bit K is
5/3 of a 3-bit K, so ~11.75 + 7.05 = **~18.8 KB/tok** if it reuses turbo3's
block structure exactly, or ~24 KB/tok with a more generous scale/norm budget.
Either lands between turbo3 (14.1) and fp8 (34.0), which is the whole point.

**Success bar, pre-declared:** recover **at least half** the turbo3 -> turbo3v
catastrophic gain (114 -> 52, so a bar of <= 83) at **under 24 KB/tok**. Below
that bar the rung is not worth its complexity: turbo3 is cheaper and fp8 is
better, and this would just be a third thing to maintain between them.

**Kill condition:** if 5-bit K lands above fp8's 19 catastrophic AND above
24 KB/tok, stop -- that is turbo3v's failure mode repeated at a different point
and the band is simply not there on this model.

## What exists to build on

- `src/turbo3.cuh` -- the shared device+host format definition. 3-bit
  PolarQuant, baked Walsh-Hadamard rotation over 128-element groups, 8
  Lloyd-Max centroids scaled by a per-block L2 norm. `block_turbo3_0` = 50 bytes
  per 128 dims; head_dim 256 = exactly TWO groups, no padding.
  **Correctness contract: `dequant(K) == WHT(K)`**, so the attention dot uses
  `WHT(q) . dequant(K) == q.K` (WHT is orthonormal) and the pooled output is
  `WHT(true output)`, un-rotated by one inverse WHT.
- `src/prefill.cu:2477` -- turbo3 prefill legs (phase 2). Note `engine.cuh:489`
  still says batched prefill has no turbo3 leg; that comment is STALE and now
  marked so.
- `src/engine.cuh` -- `kv_kind` enum (`KV_F16/KV_FP8/KV_T3/KV_T3V`),
  `kv_bytes(bool is_v)` already sizes K and V **separately**, which is exactly
  the hook an asymmetric format needs. `Q27_KV` parsing is in `init()`.
- `tools/turbo3_test.cu` -- validates the format bit-for-bit against the CPU
  reference. The new format needs the equivalent before anything else.

## Phases

### P0 -- format + microtest (no engine changes)

Define `block_turbo5` in a new `src/turbo5.cuh` (or extend turbo3.cuh; prefer a
new header so turbo3 stays untouched and bitwise). Reuse turbo3's WHT rotation
and per-block L2 norm verbatim -- **only the centroid table and bit packing
change**: 32 Lloyd-Max centroids instead of 8, 5 bits per element.

Packing for 128 dims at 5 bits = 640 bits = 80 bytes, plus the norm. Land on a
block size that keeps 4-byte alignment for coalesced 128-byte warp reads; 84 B
is the natural target (80 + f32 norm), giving 2 blocks per (kv_head) row.

Gate: device quant == CPU reference bit-for-bit, round-trip cosine (expect
~0.998 vs turbo3's 0.983), and the read contract `WHT(q).deq(K) == q.K` cosine.
Model this on `tools/turbo3_test.cu` exactly. **Do not proceed past a failing
microtest** -- the turbo3 port's one debugging detour was a hand-typed test
oracle, not the kernel.

### P1 -- decode path behind `Q27_KV=turbo5k`

- `kv_kind` gains `KV_T5K`; `kv_bytes(is_v)` returns the 5-bit size for K and
  the existing turbo3 size for V. This is already asymmetric-capable.
- `k_kv_store` gains a turbo5 K leg (V keeps the turbo3 leg unchanged).
- fd2 decode attention gains a 5-bit K dequant path. The fd2 lane layout (lane
  `l` owns dims `4l..4l+3` and `128+4l..`) maps onto the two 128-groups with
  zero reshuffle, same as turbo3 -- **verify this still holds at 5 bits**, since
  the packing crosses byte boundaries differently.
- fp16/fp8/turbo3 must stay **bitwise** -- new format is additive, selected only
  by the env var.

Gate: canonical `a2982c5197c627551b27d76a0a94b220` EXACT (the CLI defaults to
fp16, so the feature is inert there); `tools/ninv_test.cu` ALL PASS; needle
6/6 at depth.

### P2 -- prefill leg

Mirror `prefill.cu:2477`'s turbo3 store. Without this the format is
decode-only and `--nll-long` cannot measure it (see the gotcha below).

### P3 -- the measurement that decides it

Re-run the 08-01 tail study with turbo5k added. The harness already exists:

    ./build/q27 <model> --nll scratchpad/t3_quality/corpus/agentic_req0031.i32 \
        --nll-long 65536 --ctx 69632 --nll-dump <out>.bin

for `Q27_KV` in `""` (fp16 reference), `fp8`, `turbo3`, `turbo3v`, `turbo5k`,
then the analysis from the 08-01 entry: mean |d|, p99.9, |d|>1 count, and
catastrophic (fp16 NLL < 0.1 and format NLL > 1.0). ~30 s per leg at 64K.

Report against the pre-declared bar above. If it passes, the follow-on question
is whether it displaces turbo3 as the **Ampere** default, where fp8 is
unavailable and the current choice is turbo3-or-nothing at 262K.

## Traps, banked

- **Free the GPU before any canonical check.** A co-located CLI next to the
  production server OOMs and `grep generated: | md5sum` then returns
  `d41d8cd98f00b204e9800998ecf8427e` -- the md5 of empty -- which reads as a
  broken canonical. Cost a scare on 08-01 and is already recorded against
  commit `f551561`.
- **fp16 KV does not fit at 154K.** 68 KB/tok x 154160 = 11.1 GB beside 17.73 GB
  of weights OOMs a 32 GB card. Any fp16-referenced study runs at 64K. This is
  why the 07-16 gate used fp8 as its reference and could not see the tail.
- **Means hide this entirely.** The whole reason this work exists is that
  bucket-mean NLL reported +0.39% while p99.9 was +5.49. Report tails.
- **A symmetric tail against a lossy reference is ambiguous.** turbo3-vs-fp8
  looked symmetric (worse at 1425 positions, better at 1439) and only the fp16
  reference disambiguated it. Always reference fp16.
- The article's own finding is that **weight precision masks cache artifacts**,
  so these ratios are specific to the default 5.25 bpw tier. If turbo5k is
  evaluated for q4s, re-measure.

## Not in scope

TCQ (trellis-coded quantization). anbeeld measures turbo3_tcq at 81.56% vs
plain turbo3's 76.12% on their metric, so it is a real lever, but it is a
different algorithm rather than a bit-width change and belongs in its own plan.
